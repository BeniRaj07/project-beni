Awaaz — runtime architecture

A single local Python process serves a Gradio page. Every typed or spoken message goes through the same pipeline: transcribe (voice only), Groq classifies the intent, one handler routes and fetches the data, Claude writes the reply, then it is optionally spoken. Only Groq, Claude, the speech services and the public data APIs sit outside your machine.

primary path (numbered) leaves your machine (HTTPS) supporting local call

Primary path, step by step

  1. Browser → app.py: typed text, or a recorded clip uploaded by the mic/VAD script in theme.py.
  2. Transcribe (speech_to_text.py): Groq Whisper; language forced by the EN / ने switch when set.
  3. respond() in conversation.py keeps the follow-up state (pending question, last city, last 40 messages).
  4. Classify (intent_classifier.py): Groq returns a JSON intent with a confidence; Pydantic validates it, bad fields become None. Claude is never asked to classify.
  5. Dispatch: HANDLERS[intent] in handlers.py.
  6. Handler calls domain services, then the response writer sends Claude the intent, only the retrieved context and a bounded history (1 Groq call + 1 Claude call per message).
  7. Speak (text_to_speech.py): text shows first, audio follows; a TTS failure never hides the reply.
  8. Back to the browser as chat text plus an audio file.

Trust boundaries

  • T1 Browser ↔ local server. Bound to 127.0.0.1; set APP_AUTH=user:pass before exposing it. No other auth exists.
  • T2 Machine ↔ internet. Every third-party call is HTTPS with a key from .env. Whatever is in a prompt or audio clip leaves the machine here.
  • T3 Process ↔ disk. data/*.json is plain, unencrypted, gitignored. Personal facts are searched locally and only the few relevant ones go into a prompt.

Intent handlers (21)

  • Chat: greeting, general_ai, out_of_scope
  • Reminders: create, list, update, delete
  • Tasks: create, list, update, complete, delete
  • Information: weather, daily_briefing, nepal_news
  • Football: news, league_table, league_results, fixtures
  • Memory: save_personal_info, personal_query

A handler that is missing a field stores a pending question; the next message is merged into it.

Data at rest (T3)

  • conversations.json, reminders.json, tasks.json, settings.json, personal_context.json
  • Read-modify-write goes through JsonStore with a file lock and Pydantic models, so the scheduler thread and a chat request cannot double-fire a reminder.
  • Generated audio lives in data/audio/ and is deleted after about 2 hours.

Background and side channels

  • Scheduler (APScheduler): checks due reminders every 20 s and cleans audio every 30 min. Reminders only fire while the app is running; overdue ones are announced at start-up.
  • UI timers: the page polls for fired reminders every 15 s and refreshes the Tasks / Reminders / Weather / System cards every 30 s.
  • Browser only: wake-word listening, voice-activity detection and barge-in run in the page's JavaScript; nothing is sent until a clip is uploaded.
  • notch-app/: an optional Electron pill that reads the JSON files directly every 8 s. It never talks to the Python process.

How it fails

  • Missing key, quota or network errors become a friendly English or Nepali message, never a stack trace (conversation.respond).
  • TTS tries the next engine in order; if all fail the text reply is still shown.
  • Groq and Claude failures are handled separately (each names its own service in the message). The Claude error text includes the API status so a bad key, no credit or an unavailable model is visible in the chat.
